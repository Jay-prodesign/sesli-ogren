# LA-0036 — Passwordless account entry + session restore

- **Status:** DONE
- **Handoff:** Post-LA-0035 first-commercial-V0 completeness
- **Executor:** ChatGPT (bounded reversible engineering)
- **Owner / verifier:** Brain

## Objective
Close the canonical V0 create/sign-in gap without breaking learner identity continuity. Existing sessions restore as-is; a fresh no-session installation must explicitly enter a passwordless email account flow instead of silently creating an anonymous Auth user.

## Authoritative source references
- D-054 / V0_PRODUCT_SCOPE_v2.0 — create/sign in is part of the required core V0 end-to-end flow.
- RELEASE_MODEL_V0_V1_FINAL — real onboarding and account flow are required for a sellable V0.
- Supabase Auth current guidance — email OTP supports sign-in/sign-up without passwords; anonymous users require later identity linking to become recoverable permanent users.
- D-066 / D-077 — shortest production path; live external auth evidence may remain release-gated and must not become proof-only infrastructure.

## In scope
- Restore an existing Supabase Auth session before opening learner data.
- Fresh no-session startup shows email OTP account entry.
- Request an email OTP with account creation allowed.
- Verify six-digit OTP and open AppRuntime under the verified Auth user id.
- Preserve fail-closed behavior when Supabase client-safe configuration is missing.
- Remove the product path that silently creates a new anonymous Auth user.
- Widget regression for request/verify behavior.
- Document the external Supabase email-template/live-delivery release configuration.

## Out of scope
- Migrating/linking an already-anonymous learner to email identity.
- Anonymous-to-existing-account merge/conflict resolution.
- OAuth/Google/Apple sign-in.
- Password authentication/reset.
- Hosted Supabase database deployment.
- SMTP/vendor activation or paid email service.
- Billing/payment activation.

## Dependencies
- LA-0035 first-run onboarding is DONE.
- Existing Supabase Flutter client and Auth session persistence.
- Client-safe SUPABASE_URL + SUPABASE_PUBLISHABLE_KEY at runtime.
- Hosted Email Auth + OTP template configuration before live acceptance.

## Required tests / evidence
- Account-entry widget requests code for entered email.
- Six-digit OTP verification returns the authenticated learner and continues into runtime.
- Incomplete OTP never invokes verification.
- Missing Supabase client configuration still fails closed without opening learner data.
- Canonical format, Flutter analyze, expanded Flutter tests and bootstrap validation pass.
- Live email receipt/OTP verification remains a release-gate evidence item until hosted configuration is available.

## Security invariants
1. No secret/service-role key enters Flutter or repository source.
2. Learner identity comes from verified Supabase Auth user id, never email text.
3. Existing session user id is preserved exactly.
4. No-session startup does not silently create a disposable identity.
5. OTP verification failure never opens learner data.
6. Anonymous-to-permanent identity migration is not guessed or auto-merged in this tranche.

## Rollback / migration notes
Client-only auth-flow change; no local SQLite or server database migration. Reverting the account-entry screen and restoring the previous startup call returns the old behavior, though silent anonymous creation is intentionally no longer desired.

## Escalation conditions
- Stop before changing hosted Auth provider settings, SMTP, production credentials, or paid services.
- Stop if an existing anonymous learner must be merged into another permanent account; that needs an explicit identity/data-conflict contract.
- Do not claim live auth/release readiness until a real OTP email round trip is verified.

## Acceptance criteria
1. Existing session opens the same learner runtime.
2. No session renders account entry rather than product data.
3. Valid OTP verification opens the verified learner runtime.
4. Invalid/incomplete OTP does not open runtime.
5. No new anonymous account is created automatically.
6. Missing client-safe Supabase config fails closed.
7. Repository validations pass.

## Expected return
A real user-facing create/sign-in entry for fresh users, with stable existing-session continuity and no silent disposable identity creation.
